Image Optimization for Core Web Vitals

How image optimization improves Core Web Vitals: LCP, CLS, and INP explained, with practical fixes for slow pages — compression, resizing, and formats.

Core Web Vitals are the speed scores Google uses to judge your pages. They measure how fast the largest content appears, how stable the layout is, and how quickly the page responds.

Images affect all three scores. A heavy hero delays the largest paint, a missing width causes layout shift, and a bloated page slows interaction.

This article explains how image optimisation moves each score, and what to fix first on a slow page.

What Are Core Web Vitals?

Core Web Vitals are three metrics that describe the user experience of loading a page. They are measured on real visitors, not in a lab.

Largest Contentful Paint, or LCP, measures how long the biggest visible element takes to appear. On most pages, that element is an image.

Cumulative Layout Shift, or CLS, measures how much the page moves while it loads. Images without dimensions are the most common cause.

Interaction to Next Paint, or INP, measures how quickly the page responds to clicks and taps. Heavy pages with many large images respond more slowly.

Google uses these scores in search rankings. Faster pages rank better, and image optimisation is the biggest single lever most sites have.

LCP: Why the Hero Image Decides It

LCP is usually decided by the hero image. It is the largest element on the screen, so the page is not considered loaded until it appears.

A 5MB hero can take seconds to download on a mobile connection. During those seconds, the visitor sees a blank space where the hero belongs.

Compressing the hero to a few hundred kilobytes cuts that wait sharply. The image appears sooner, and the LCP score improves immediately.

Dimensions matter too. A hero served at twice its display size wastes bandwidth on pixels nobody sees, delaying the paint further.

Preloading the hero helps as well. Telling the browser early about the most important image lets it start downloading before anything else.

Fixing a Slow LCP Step by Step

First, find the LCP element. Speed tools name it directly, and it is usually the hero image or a large banner.

Second, optimise that image with the Web Image Optimizer. Use the hero preset, which sizes it correctly and keeps the quality high.

Third, make sure lazy loading is off for the hero. Delaying the most important image is the most common LCP mistake.

Fourth, preload the hero in the page head. The browser then fetches it first, before stylesheets and scripts compete for bandwidth.

Fifth, re-test the page. The LCP time should have dropped sharply, often by several seconds on mobile.

CLS: How Images Shift the Layout

CLS measures unexpected movement. When an image loads late without reserved space, the text below it jumps down, and the visitor loses their place.

The fix is simple: always include width and height in the image tag. The browser then reserves the space before the image arrives.

The optimiser's Copy Image Tag button includes those dimensions automatically. Pasting the tag as given prevents the shift entirely.

Aspect ratio matters as well. An image with the wrong ratio distorts when it fills its reserved space, which looks broken even without shifting.

Check the page by loading it fresh and watching for movement. Any jump you see is a CLS problem waiting to hurt your score.

INP: How Image Weight Slows Interaction

INP measures responsiveness. When a visitor taps a button, the page should react quickly, and heavy pages react slowly.

Images affect INP indirectly. A page with megabytes of images keeps the browser busy downloading and decoding, which delays its response to taps.

Lazy loading helps here. Images below the fold do not need to download before the page becomes interactive, so deferring them frees the browser.

Decoding large images also costs time. An oversized image takes longer to decode than a correctly sized one, even after it downloads.

The fix is the same as for LCP: right-size every image, lazy-load the ones below the fold, and keep the total page weight low.

Measuring Core Web Vitals Properly

Measure on real devices, not just on a fast office connection. Most visitors browse on phones, and mobile scores are what count.

Use the free speed tools to get a baseline. Note the LCP, CLS, and INP numbers before changing anything.

Change one thing at a time. Optimising the hero, then re-testing, tells you exactly how much the hero was costing.

Re-test after every round of fixes. Scores move in steps, and each step shows whether the last change helped.

Remember that scores vary by visitor. A single test is a snapshot; several tests across days give the real picture.

Setting an Image Budget for a Page

An image budget caps the total weight of images on a page. A common budget is 1MB for a content page and 2MB for a gallery.

Divide the budget by the number of images. Ten images sharing a 1MB budget get 100KB each, which is a sensible target.

Give the hero a larger share. It deserves 300KB or 400KB, while supporting images take 100KB each.

Enforce the budget in your publishing workflow. A checklist that includes image weight stops heavy images from reaching the live site.

Review the budget when the design changes. A new theme with larger images needs a larger budget, or smaller images to match.

Formats and Core Web Vitals

WebP is the best format for Core Web Vitals. It is smaller than JPG at the same quality, which helps LCP directly.

Modern browsers all support WebP. The format is no longer a risk for mainstream sites, and the speed gain is real.

JPG remains the fallback for older systems. When compatibility matters more than speed, JPG is the safe choice.

PNG hurts Core Web Vitals for photos. Its large files delay LCP and bloat the page, so reserve PNG for graphics only.

Serve the smallest format the visitor's browser supports. That single rule captures most of the format benefit available.

Responsive Images and Resolution Switching

Responsive images serve different sizes to different screens. A phone gets a small file, while a desktop gets a larger one.

The HTML srcset attribute lists the available sizes, and the browser picks the right one for the screen it is running on.

This matters for LCP on mobile. A phone downloading a desktop-sized hero wastes seconds on pixels its small screen cannot show.

Generate two or three sizes per image: a mobile size, a tablet size, and a desktop size. The optimiser's presets make each one in a click.

Test on a real phone after adding responsive images. The LCP improvement on mobile is often dramatic.

Common Core Web Vitals Mistakes

Lazy-loading the hero is the most common mistake. It delays the LCP element and guarantees a poor score.

Missing width and height is the second. Images without dimensions shift the layout and damage the CLS score.

Serving oversized images is the third. A 4000-pixel image displayed at 800 pixels wastes bandwidth and delays the paint.

Forgetting below-fold images is the fourth. A page can have a fast hero and still be slow overall if twenty unoptimised thumbnails follow it.

Fixing these four mistakes resolves most image-related Core Web Vitals problems. They are simple, and they work.

What to Fix First: A Priority Order

Fix the LCP image first. It has the biggest single effect on the score and on the visitor's first impression.

Fix missing dimensions second. Adding width and height to every image tag is quick and eliminates layout shift.

Fix the total weight third. Lazy-load below-fold images and compress the rest, bringing the page under its budget.

Fix responsiveness fourth. Responsive images help mobile visitors most, and mobile scores matter most.

Re-test after each step. The scores will tell you when the page is good enough, and when more work is needed.

Field Data vs Lab Data

Core Web Vitals come in two kinds: lab data from a single test, and field data from real visitors over weeks.

Lab data is instant and repeatable. It tells you how the page performs on a fast connection in a controlled test.

Field data is slower but honest. It reflects real visitors on real phones with real connections, including the slow ones.

Google ranks on field data. A page that scores well in the lab but poorly in the field will still rank poorly.

Use lab data to find problems and field data to confirm fixes. The two together give the full picture of your page speed.

When the LCP Element Is Not an Image

Sometimes the largest paint is a block of text, not an image. In that case, image optimisation helps less, and fonts and stylesheets matter more.

Check what the speed tool names as the LCP element. If it is text, look at font loading and render-blocking styles.

Images can still delay a text LCP. A heavy background image or a slow-loading logo can hold up the whole page.

Optimise the images anyway. A lighter page helps every metric, even when the LCP element itself is text.

Do not optimise blindly. Knowing which element drives the score tells you where to spend your effort.

CLS Beyond Images: Fonts and Ads

Images are the most common CLS cause, but not the only one. Web fonts and ads also shift the layout as they load.

Fonts shift text when they swap in. Using font-display swap with a close fallback reduces the visible jump.

Ads shift content when they load late. Reserving space for ad slots prevents the page from jumping when the ad arrives.

Fix images first, since they are the easiest win. Then look at fonts and ads if the CLS score is still poor.

A page with zero layout shift feels calm and professional. Visitors notice the stability even if they cannot name it.

INP and Heavy Scripts

Images are rarely the main INP problem. Heavy JavaScript is usually the bigger cause of slow interaction.

Still, image work helps INP. A lighter page leaves the browser more time to respond to taps and clicks.

Decode costs matter too. An oversized image takes longer to decode than a correctly sized one, and decoding blocks interaction.

Keep third-party scripts lean. Analytics, chat widgets, and social embeds all compete with your page for the browser's attention.

Think of INP as a budget. Every script and image spends from it, and the page must respond before the budget runs out.

Mobile First: Why Phone Scores Matter Most

Most visitors browse on phones, and Google ranks on mobile scores. A page that is fast on desktop but slow on mobile will rank poorly.

Phones have slower connections and weaker processors. The same hero image takes longer to download and decode on a phone than on a laptop.

Optimise for the phone first. A page that is fast on mobile is fast everywhere, while the reverse is not true.

Test on a real phone, not just in a desktop simulator. The simulator hides the real-world slowness that visitors actually feel.

Mobile-first optimisation is not a trend. It is how the web works now, and the scores reflect it.

Ongoing Monitoring of Core Web Vitals

Core Web Vitals change over time. New images, new plugins, and new themes can all hurt the scores silently.

Check the scores monthly at minimum. A regular check catches problems before they affect rankings.

Set up alerts if your platform supports them. An alert when LCP crosses the threshold saves weeks of slow rankings.

Review the scores after every redesign. A new theme changes every image slot, and the old optimisations may no longer fit.

Speed is a habit, not a project. The sites that stay fast are the ones that keep watching.

A Final Check Before You Publish

Run the speed tool one last time after all fixes. Confirm LCP, CLS, and INP are all in the green range before moving on.

Load the page on a real phone over a mobile connection. The numbers in a lab test are useful, but the feeling on a phone is the truth.

Frequently asked questions

What is a good LCP score?

Google considers an LCP under 2.5 seconds good. Most pages miss that target because of a heavy hero image. Compressing the hero, serving it at the right size, and preloading it are the fastest ways to get under the threshold.

How do images cause layout shift?

When an image loads without width and height attributes, the browser does not know how much space to reserve. The image arrives late and pushes the content below it down, which counts as layout shift. Including dimensions in the tag prevents it.

Does lazy loading improve Core Web Vitals?

Yes, for below-fold images. Deferring them frees bandwidth for the hero and makes the page interactive sooner. Never lazy-load the hero or logo, since delaying them hurts LCP directly.

Why is my mobile LCP score worse than desktop?

Mobile connections are slower and phone processors are weaker, so the same hero image takes longer to download and decode. Optimizing the hero, serving a smaller mobile version, and preloading it will close most of the gap.

Can image optimization alone fix a poor Core Web Vitals score?

Often yes, when images are the main problem. A page with 5MB of images will improve dramatically once they are optimized. If the score stays poor, the problem may be slow hosting, heavy scripts, or render-blocking stylesheets instead.

How often should I re-check Core Web Vitals?

After every design change and at least once a month. New images, new themes, and new plugins can all hurt the scores silently. A monthly check catches problems before they affect rankings.
