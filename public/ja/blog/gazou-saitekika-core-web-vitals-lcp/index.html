画像最適化でCore Web Vitalsを改善する方法

Core Web Vitalsは、Googleがページを判断するために使う速度スコアです。最大のコンテンツが表示されるまでの速さ、レイアウトの安定性、ページの応答の速さを測ります。

画像は3つのスコアすべてに影響します。重いヒーローは最大の表示を遅らせ、幅のない画像はレイアウトのずれを引き起こし、膨らんだページは操作の応答を遅くします。

この記事では、画像の最適化が各スコアをどう動かすか、遅いページで何を最初に修正すべきかを解説します。

Core Web Vitalsとは

Core Web Vitalsは、ページ読み込みのユーザー体験を表す3つの指標です。ラボではなく、実際の訪問者で測定されます。

Largest Contentful Paint（LCP）は、画面上で最大の要素が表示されるまでの時間を測ります。ほとんどのページでは、その要素が画像です。

Cumulative Layout Shift（CLS）は、読み込み中にページがどれだけ動くかを測ります。寸法のない画像が最も一般的な原因です。

Interaction to Next Paint（INP）は、クリックやタップにページがどれだけ速く応答するかを測ります。大きな画像の多い重いページは、応答が遅くなります。

Googleは検索順位にこれらのスコアを使います。速いページは順位がよく、画像の最適化はほとんどのサイトが持つ最大の手段です。

LCP：ヒーロー画像が決める理由

LCPはたいてい、ヒーロー画像で決まります。画面上で最大の要素なので、それが表示されるまでページは読み込まれたとみなされません。

5MBのヒーローは、モバイル回線でダウンロードに数秒かかることがあります。その間、訪問者はヒーローがあるはずの場所に空白を見ます。

ヒーローを数百キロバイトに圧縮すれば、その待ち時間は大幅に短縮します。画像が早く表示され、LCPスコアはすぐに改善します。

寸法も重要です。表示サイズの2倍で提供されるヒーローは、誰も見ないピクセルに帯域幅を浪費し、表示をさらに遅らせます。

ヒーローのプリロードも助けになります。ブラウザに最も重要な画像を早めに伝えることで、他のものより先にダウンロードを開始できます。

遅いLCPを段階的に修正する

まず、LCPの要素を見つけます。速度ツールが直接名前を挙げ、たいていヒーロー画像や大きなバナーです。

次に、その画像をWeb画像最適化ツールで最適化します。ヒーロープリセットを使い、正しくサイズを設定して画質を高く保ちます。

次に、ヒーローの遅延読み込みがオフになっていることを確認します。最も重要な画像を遅らせることが、最も一般的なLCPの間違いです。

次に、ページのheadでヒーローをプリロードします。ブラウザはそれを最初に取得し、スタイルシートやスクリプトと帯域幅を競う前にダウンロードします。

最後に、ページを再テストします。LCPの時間は大幅に下がっているはずで、モバイルではたいてい数秒の改善です。

CLS：画像がレイアウトをずらす仕組み

CLSは、予期しない動きを測ります。画像が予約されたスペースなしに遅れて読み込まれると、下のテキストが下に飛び、訪問者は読んでいる場所を見失います。

修正はシンプルです。画像タグに必ず幅と高さを含めます。ブラウザは画像が届く前にスペースを確保します。

最適化ツールの「画像タグをコピー」ボタンは、それらの寸法を自動で含みます。タグをそのまま貼れば、ずれは完全に防げます。

アスペクト比も重要です。比率の間違った画像は、予約されたスペースを埋めるときにゆがみ、ずれがなくても壊れて見えます。

ページを新しく読み込んで動きを観察し、確認します。見える飛びはすべて、スコアを悪化させるCLSの問題です。

INP：画像の重さが操作を遅くする仕組み

INPは応答性を測ります。訪問者がボタンをタップしたとき、ページは速く反応すべきで、重いページは反応が遅くなります。

画像はINPに間接的に影響します。メガバイト単位の画像があるページは、ブラウザをダウンロードとデコードで忙しくし、タップへの応答を遅らせます。

遅延読み込みがここで助けになります。画面の下部の画像は、ページが操作可能になる前にダウンロードする必要がないので、先送りすればブラウザが解放されます。

大きな画像のデコードにも時間がかかります。大きすぎる画像は、正しくサイズ設定されたものより、ダウンロード後もデコードに時間がかかります。

修正はLCPと同じです。すべての画像を適切なサイズにし、画面の下部の画像は遅延読み込みし、ページの合計重量を低く保ちます。

Core Web Vitalsを正しく測る

速いオフィスの回線だけでなく、実際の端末で測りましょう。ほとんどの訪問者はスマホで閲覧し、モバイルのスコアが重要です。

無料の速度ツールで基準値を測ります。何も変える前に、LCP、CLS、INPの数字をメモします。

1回に1つのことだけを変えます。ヒーローを最適化して再テストすれば、ヒーローがどれだけコストだったかが正確にわかります。

修正を1回行うたびに再テストします。スコアは段階的に動き、各段階が前回の変更が役立ったかを示します。

スコアは訪問者によって変わることを忘れないでください。1回のテストはスナップショットです。数日間にわたる数回のテストが、実際の姿を示します。

ページの画像予算を設定する

画像予算は、ページ上の画像の合計重量の上限です。一般的な予算は、コンテンツページで1MB、ギャラリーで2MBです。

予算を画像の数で割ります。1MBの予算を10枚で共有すれば、1枚あたり100KBになり、妥当な目標です。

ヒーローには大きな割合を与えます。300KBや400KBに値し、補助画像は1枚100KBずつです。

予算を公開のワークフローで守ります。画像の重さを含むチェックリストが、重い画像の公開サイト到達を防ぎます。

デザインが変わったら予算を見直します。画像が大きく表示される新しいテーマは、大きな予算か、それに合わせた小さな画像が必要です。

形式とCore Web Vitals

WebPはCore Web Vitalsに最適な形式です。同じ画質でJPGより小さく、LCPに直接効きます。

最新のブラウザはすべてWebPに対応しています。この形式は、一般的なサイトではもはやリスクではなく、速度の向上は確かです。

JPGは古いシステムのフォールバックとして残ります。速度より互換性が重要な場合、JPGが安全な選択です。

PNGは写真でCore Web Vitalsを悪化させます。大きなファイルがLCPを遅らせ、ページを膨らませるので、PNGは図形だけに使いましょう。

訪問者のブラウザが対応する最小の形式を提供しましょう。この1つのルールが、形式から得られる効果のほとんどを捉えます。

レスポンシブ画像と解像度の切り替え

レスポンシブ画像は、画面ごとに異なるサイズを提供します。スマホは小さなファイルを、デスクトップは大きなファイルを受け取ります。

HTMLのsrcset属性が、利用可能なサイズを一覧表示し、ブラウザが実行中の画面に適したものを選びます。

これはモバイルのLCPに重要です。デスクトップサイズのヒーローをダウンロードするスマホは、小さな画面では表示できないピクセルに数秒を浪費します。

画像ごとに2〜3サイズ作ります。モバイル用、タブレット用、デスクトップ用です。最適化ツールのプリセットが、それぞれを1クリックで作ります。

レスポンシブ画像を追加したら、実際のスマホでテストします。モバイルでのLCP改善は、たいてい劇的です。

よくあるCore Web Vitalsの間違い

ヒーローの遅延読み込みが、最も多い間違いです。LCPの要素を遅らせ、低いスコアを確実にします。

幅と高さの欠落が2番目です。寸法のない画像はレイアウトをずらし、CLSスコアを損ないます。

大きすぎる画像の提供が3番目です。800ピクセルで表示される4000ピクセルの画像は、帯域幅を浪費し、表示を遅らせます。

画面の下部の画像を忘れることが4番目です。ヒーローが速いページでも、最適化されていないサムネイルが20枚続けば、全体としては遅いままです。

この4つの間違いを修正すれば、画像関連のCore Web Vitalsの問題のほとんどが解決します。シンプルで、効果があります。

最初に修正すべき順番

まずLCPの画像を修正します。スコアと訪問者の第一印象に、最も大きな単独の効果があります。

次に、不足している寸法を修正します。すべての画像タグに幅と高さを追加するのは速く、レイアウトのずれをなくします。

次に、合計重量を修正します。画面の下部の画像を遅延読み込みし、残りを圧縮して、ページを予算以下にします。

次に、レスポンシブ対応を修正します。レスポンシブ画像はモバイルの訪問者に最も役立ち、モバイルのスコアが最も重要です。

各ステップの後に再テストします。スコアが、ページが十分によいときと、さらなる作業が必要なときを教えてくれます。

フィールドデータとラボデータ

Core Web Vitalsには2種類あります。1回のテストからのラボデータと、数週間にわたる実際の訪問者からのフィールドデータです。

ラボデータは即座に再現できます。管理されたテストで、速い回線でのページのパフォーマンスを示します。

フィールドデータは遅いですが正直です。遅い回線を含め、実際のスマホでの実際の訪問者を反映します。

Googleはフィールドデータで順位を決めます。ラボではよくても、フィールドで悪いページは、順位も悪くなります。

ラボデータで問題を見つけ、フィールドデータで修正を確認します。両方を合わせることで、ページ速度の全体像がわかります。

LCPの要素が画像ではない場合

最大の表示が、画像ではなくテキストのブロックであることがあります。その場合、画像の最適化の効果は小さく、フォントとスタイルシートが重要になります。

速度ツールがLCPの要素として何を挙げているか確認します。テキストなら、フォントの読み込みと表示を妨げるスタイルを確認します。

画像は、テキストのLCPでも遅らせることがあります。重い背景画像や遅いロゴが、ページ全体を止めることがあります。

いずれにせよ、画像は最適化しましょう。軽いページはすべての指標に役立ちます。LCPの要素自体がテキストでも同じです。

盲目的に最適化しないこと。どの要素がスコアを動かすかを知ることが、労力をどこに使うべきかを教えてくれます。

画像以外のCLS：フォントと広告

画像は最も一般的なCLSの原因ですが、唯一ではありません。Webフォントと広告も、読み込み時にレイアウトをずらします。

フォントは、入れ替わるときにテキストをずらします。font-display: swapと近いフォールバックを使うと、目に見える飛びが減ります。

広告は、遅れて読み込まれるとコンテンツをずらします。広告枠のスペースを予約すれば、広告が届いたときにページが飛ぶのを防げます。

まず画像を修正しましょう。最も簡単な改善だからです。CLSスコアがまだ悪い場合は、次にフォントと広告を確認します。

レイアウトのずれがないページは、落ち着いてプロらしく感じられます。訪問者は、その安定性を名前は言えなくても感じ取ります。

INPと重いスクリプト

画像がINPの主な問題になることはめったにありません。重いJavaScriptが、たいてい操作の遅さの大きな原因です。

それでも、画像の作業はINPに役立ちます。軽いページは、ブラウザがタップやクリックに応答する時間を多く残します。

デコードのコストも重要です。大きすぎる画像は、正しくサイズ設定されたものよりデコードに時間がかかり、デコードが操作を妨げます。

サードパーティのスクリプトは軽く保ちましょう。分析、チャットウィジェット、SNSの埋め込みはすべて、ブラウザの注意をページと奪い合います。

INPを予算だと考えましょう。すべてのスクリプトと画像がそこから使い、ページは予算が尽きる前に応答しなければなりません。

モバイル優先：スマホのスコアが最も重要な理由

ほとんどの訪問者はスマホで閲覧し、Googleはモバイルのスコアで順位を決めます。デスクトップでは速くても、モバイルでは遅いページは順位が悪くなります。

スマホは回線が遅く、プロセッサも弱いです。同じヒーロー画像でも、スマホのほうがダウンロードとデコードに時間がかかります。

まずスマホ向けに最適化しましょう。モバイルで速いページはどこでも速く、逆は成り立ちません。

デスクトップのシミュレーターだけでなく、実際のスマホでテストします。シミュレーターは、訪問者が実際に感じる現実の遅さを隠します。

モバイル優先の最適化は流行ではありません。今のWebのあり方で、スコアはそれを反映しています。

Core Web Vitalsの継続的な監視

Core Web Vitalsは時間とともに変わります。新しい画像、新しいプラグイン、新しいテーマが、すべて静かにスコアを悪化させることがあります。

スコアは最低でも月1回確認します。定期的な確認が、順位に影響する前に問題を見つけます。

プラットフォームが対応している場合は、アラートを設定します。LCPがしきい値を超えたときのアラートが、数週間の遅い順位を防ぎます。

デザインを変更するたびに、スコアを確認します。新しいテーマはすべての画像の場所を変え、古い最適化はもう合わないかもしれません。

速度は習慣であって、プロジェクトではありません。速さを保つサイトは、見守り続けるサイトです。

公開前の最終確認

すべての修正の後、速度ツールを最後にもう一度実行します。公開に進む前に、LCP、CLS、INPがすべてグリーンの範囲にあることを確認します。

モバイル回線の実際のスマホでページを開きます。ラボテストの数字は役立ちますが、スマホでの体感が真実です。

最適化ツールの詳しいガイドは、Web画像最適化ツールの完全ガイドをご覧ください。手順版はWebサイトの表示速度を上げる画像最適化の方法です。シンプルなサイズ目標には、200KB圧縮ツールと複数画像一括圧縮ツールが重い作業を処理します。

よくある質問

よいLCPスコアとは何ですか？

Googleは、LCPが2.5秒未満を良好としています。ほとんどのページは、重いヒーロー画像のためにその目標に届きません。ヒーローを圧縮し、適切なサイズで提供し、プリロードすることが、しきい値を下回る最も速い方法です。

画像はどうやってレイアウトのずれを引き起こしますか？

画像が幅と高さの属性なしに読み込まれると、ブラウザは確保すべきスペースがわかりません。画像が遅れて届き、下のコンテンツを押し下げるので、レイアウトのずれとして数えられます。タグに寸法を含めれば防げます。

遅延読み込みはCore Web Vitalsを改善しますか？

はい。画面の下部の画像については、そうです。先送りすることで、ヒーローの帯域幅が解放され、ページが早く操作可能になります。LCPに直接悪影響するので、ヒーローやロゴを遅延読み込みしないでください。

モバイルのLCPスコアがデスクトップより悪いのはなぜですか？

モバイル回線は遅く、スマホのプロセッサは弱いので、同じヒーロー画像でもダウンロードとデコードに時間がかかります。ヒーローを最適化し、小さいモバイル版を提供し、プリロードすれば、差のほとんどが埋まります。

画像の最適化だけで、悪いCore Web Vitalsスコアを修正できますか？

画像が主な問題の場合、たいてい可能です。5MBの画像があるページは、最適化すれば劇的に改善します。スコアがまだ悪い場合は、遅いホスティング、重いスクリプト、表示を妨げるスタイルシートが原因かもしれません。

Core Web Vitalsはどれくらいの頻度で再確認すべきですか？

デザインを変更するたびに、最低でも月1回です。新しい画像、新しいテーマ、新しいプラグインが、すべて静かにスコアを悪化させることがあります。月1回の確認が、順位に影響する前に問題を見つけます。
