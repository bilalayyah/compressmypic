Base64 이미지: 삽입해야 할 때와 하지 말아야 할 때

Base64 이미지를 삽입하면 요청은 줄지만 바이트가 33% 늘고 캐싱이 안 됩니다. 크기 기준과 캐싱 계산, 결정 체크리스트를 배워보세요. 작은 아이콘·로고 삽입에 알맞은 크기 기준과 삽입·링크 선택법을 다룹니다.

이미지를 Base64로 삽입하면 공짜로 이득을 보는 것처럼 느껴집니다. 요청 하나가 줄고, 관리할 별도의 파일이 없고, 이미지는 페이지가 로드되는 순간 나타납니다.

이득은 실제 있지만 공짜는 아닙니다. 삽입된 이미지는 바이트가 3분의 1 더 들고, 따로 캐시할 수 없고, 코드를 읽고 유지하기 어렵게 만듭니다.

이 글에서는 결정 프레임워크를 알려줍니다. 크기 기준과 캐싱 계산, 그리고 삽입이 도움이 되는 상황과 해가 되는 상황입니다.

삽입 결정을 한 단락으로

이미지가 작고, 꼭 필요하고, 안정적일 때 삽입하세요. 모든 페이지에 필요한 아주 작은 아이콘은 따로 가져오면 요청 하나가 통째로 드는 경우라 완벽한 대상입니다.

이미지가 크거나, 공유되거나, 바뀌는 경우 링크하세요. 사진이나 50개 페이지에 쓰이는 로고, 매주 업데이트되는 이미지는 브라우저가 캐시할 수 있는 파일로 존재해야 합니다.

대부분의 이미지는 어느 한쪽에 분명히 속합니다. 애매한 경우는 그 사이의 이미지들이고, 이 글의 나머지는 그런 경우를 판단하는 방법에 대한 것입니다.

확신이 안 서면 측정하세요. 아래 기준이 느낌 대신 숫자로 결정할 수 있게 해줍니다.

크기 기준: 숫자

2KB 미만은 생각 없이 삽입하세요. 증가는 1KB 미만이고, 아낀 요청이 그보다 훨씬 가치가 있고, 비용을 알아차릴 사용자는 아무도 없습니다.

2KB에서 10KB 사이는 삽입이 보통 여전히 맞습니다. 증가는 기껏해야 몇 킬로바이트이고, 이미지가 작아서 캐싱이 거의 중요하지 않습니다.

10KB에서 50KB 사이는 경우마다 결정하세요. 화면 위쪽의 중요한 아이콘은 정당화될 수 있지만, 한 페이지의 장식 이미지는 아마 정당화되지 않습니다.

50KB를 넘으면 링크가 거의 항상 더 낫습니다. 증가만 해도 16KB 이상이고, 브라우저는 파일을 캐시해서 여러 페이지에서 재사용할 수 있었을 것입니다.

캐싱 계산

캐싱은 삽입의 숨은 비용입니다. 링크된 이미지는 한 번 다운로드돼 참조하는 모든 페이지에서 재사용되는 반면, 삽입된 이미지는 그 이미지를 담은 모든 페이지와 함께 다시 다운로드됩니다.

50페이지짜리 사이트의 10KB 로고를 생각해 보세요. 링크하면 한 번에 10KB가 듭니다. 삽입하면 모든 페이지에 13KB씩, 전체 방문에서 650KB가 듭니다.

이 계산은 한 페이지만 방문하면 뒤집힙니다. 한 페이지만 읽는 방문자는 삽입 비용을 한 번만 내고, 아낀 요청 덕분에 링크 버전보다 페이지가 더 빠를 수 있습니다.

결정하기 전에 트래픽 패턴을 아세요. 깊게 탐색하는 블로그는 공유 이미지를 링크해야 하고, 한 페이지 방문이 대부분인 랜딩 페이지는 자유롭게 삽입할 수 있습니다.

요청 vs 바이트: 어느 쪽이 더 비쌀까

모든 이미지 요청은 서버까지의 왕복과 연결 비용이 듭니다. 빠른 연결에서는 비용이 작지만, 느린 모바일 연결에서는 로딩 시간을 좌우할 수 있습니다.

삽입은 왕복을 완전히 없앱니다. 이미지가 HTML과 함께 도착하니 추가 대기나 추가 연결이 없고, 요청이 실패할 위험도 없습니다.

하지만 삽입은 HTML 자체에 바이트를 더하고, HTML은 렌더링을 막습니다. 삽입된 이미지가 1메가바이트인 페이지는 그 전부를 다운로드해야 뭔가 보일 수 있는 반면, 링크된 이미지가 있는 페이지는 텍스트를 먼저 렌더링할 수 있습니다.

균형은 수년 동안 바뀌었습니다. HTTP/2와 HTTP/3에서는 요청이 예전보다 저렴해졌으니, 가장 작은 이미지를 제외하면 삽입의 근거가 약해졌습니다.

아이콘과 로고: 삽입

아이콘은 삽입에 가장 좋은 대상입니다. 보통 2KB 미만으로 아주 작고, 페이지에 열두 개가 필요할 수 있는데, 링크하면 열두 번의 요청이 됩니다.

아이콘 세트에는 스프라이트 시트나 아이콘 폰트가 삽입을 대체할 수 있고, 둘 다 고려할 만합니다. 하지만 페이지에 아이콘이 한두 개라면 Data URL이 더 간단하고 구현도 빠릅니다.

로고는 판단이 더 애매합니다. 모든 페이지에 나타나는 10KB 미만의 작은 로고는 삽입하면 캐싱 손실이 되지만, 단일 랜딩 페이지의 로고는 삽입해도 괜찮습니다.

사이트 전체에서 쓰이는 로고는 링크하세요. 브라우저가 한 번 캐시하고, 첫 페이지 이후의 모든 페이지는 로고가 이미 있기 때문에 더 빨리 로드됩니다.

사진: 삽입하지 말 것

사진은 거의 절대 삽입하면 안 됩니다. 일반적인 웹 사진은 100KB에서 500KB인데, 문자열로는 130KB에서 670KB가 되고, 그 무게가 HTML 안에 들어갑니다.

HTML이 부풀면 렌더링이 지연됩니다. 브라우저는 문서 전체를 다운로드해야 뭔가 보여줄 수 있기 때문입니다. 링크된 사진이 있는 페이지는 텍스트를 먼저 렌더링하고 사진은 도착하는 대로 채웁니다.

사진은 아이콘보다 자주 바뀝니다. 사진을 교체할 때마다 문자열이 담긴 코드를 편집해야 하는데, 이는 오류가 나기 쉽고 검토하기 어렵습니다.

유일한 예외는 오프라인에서 동작해야 하는 단일 파일 문서입니다. 삽입된 사진 하나가 있는 보고서나 이메일은 받아들일 수 있습니다. 이미지가 나타날 다른 방법이 없기 때문입니다.

CSS 배경과 패턴

CSS에서 작게 반복되는 패턴과 질감은 삽입에 좋은 대상입니다. 배경에 반복되는 2KB 타일은 비용이 적고, 스타일시트를 쓰는 모든 페이지에서 요청을 아껴줍니다.

장식용 그라데이션과 도형은 이미지 없이 순수 CSS로 만드는 게 더 좋습니다. CSS로 쓴 그라데이션은 수십 문자밖에 안 들고 완벽하게 확대됩니다.

큰 배경 사진은 링크 상태로 두세요. 200KB 히어로 배경은 스타일시트 안에서 270KB가 되고, 스타일시트는 렌더링을 막기 때문에 페이지 전체가 이를 기다립니다.

배경 이미지가 CSS에 삽입되면 스타일시트와 따로 캐시할 수 없습니다. CSS 한 줄을 바꾸면 브라우저는 삽입된 모든 이미지와 함께 다시 다운로드해야 합니다.

HTML 이메일: 작은 것은 삽입, 큰 것은 링크

이메일은 삽입이 선택이 아니라 필요한 경우가 많은 유일한 곳입니다. 많은 클라이언트가 기본적으로 원격 이미지를 차단하기 때문에, 링크된 이미지는 나타나지 않을 수 있습니다.

로고와 메시지를 알아볼 수 있게 만드는 작은 장식 이미지를 삽입하세요. 이메일이 제대로 보이려면 반드시 나타나야 하는 이미지들입니다.

큰 사진은 대신 링크하거나 아예 빼세요. 무겁게 삽입된 사진은 휴대폰에서 메시지를 느리게 열고, 일부 클라이언트는 크기 제한을 넘는 메시지를 거부합니다.

독자가 쓰는 클라이언트에서 테스트하세요. 일부는 인라인 Base64 이미지를 차단하는데, 이는 전체 계산을 뒤집어 호스팅 이미지가 그 독자에게는 더 안전한 선택이 되게 합니다.

API 페이로드: Base64가 표준

API는 웹 페이지와 다른 세상입니다. JSON은 이진 데이터를 담을 수 없으니, JSON 페이로드 안에서 이동하는 이미지는 Base64여야 하고, 링크라는 대안은 없습니다.

여기서 결정은 삽입 대 링크가 아니라, 이미지가 애초에 페이로드에 속하는지 여부입니다. 작은 아바타나 서명 이미지는 잘 들어가지만, 수 메가바이트짜리 사진은 전용 업로드 엔드포인트가 필요할 가능성이 큽니다.

페이로드 크기 제한을 주의하세요. 많은 API가 요청을 수 메가바이트로 제한하고, 2MB 사진은 2.7MB 문자열이 돼 제한을 혼자서 넘길 수 있습니다.

API용으로 인코딩하기 전에 압축하세요. 인코딩 전에 200KB로 줄인 사진은 270KB 필드가 돼 거의 모든 페이로드 제한 안에 편하게 들어갑니다.

실제 성능 영향 측정하기

삽입에 대한 의견은 저렴하니 대신 측정하세요. 이미지를 링크한 채로 페이지를 로드하고 시간을 기록한 뒤, 이미지를 삽입한 채로 로드해서 비교하세요.

빠른 사무실 와이파이가 아니라 느린 모바일 연결에서 테스트하세요. 요청 절약은 느린 네트워크에서 가장 중요하고, 바이트 비용도 같은 네트워크에서 가장 중요하기 때문에, 테스트 없이는 균형이 정말 불분명합니다.

두 버전의 전체 페이지 무게를 확인하세요. 삽입된 페이지는 33% 증가만큼 무겁고, 그 무게는 모든 성능 감사에 나타납니다.

재방문도 확인하세요. 첫 방문은 삽입이 유리할 수 있지만, 두 번째 방문은 링크가 유리합니다. 캐시된 이미지는 두 번째에는 비용이 들지 않기 때문입니다.

Base64 삽입의 대안

SVG 이미지에는 더 저렴한 선택이 있습니다. URL 인코딩된 SVG입니다. Base64 없이 Data URL에 직접 쓴 작은 SVG는 33% 증가를 완전히 건너뛰기 때문에 더 짧습니다.

아이콘 폰트와 SVG 스프라이트 시트는 많은 작은 삽입 이미지를 하나의 캐시된 파일로 대체합니다. 요청 한 번이면 되고, 그다음 사이트의 모든 아이콘을 캐시에서 제공합니다.

HTTP/2 서버 푸시와 프리로드 힌트는 링크된 이미지를 삽입된 이미지만큼 빠르게 만들 수 있습니다. 브라우저가 이미지를 일찍 가져오기 때문에 요청 비용이 0에 가까워집니다.

자주 바뀌는 이미지에는 공격적인 캐싱을 갖춘 콘텐츠 전송 네트워크가 삽입을 완전히 이깁니다. 첫 방문은 빠르고, 그 이후의 모든 방문은 거의 공짜입니다.

보안과 콘텐츠 보안 정책

콘텐츠 보안 정책 헤더가 Data URL을 차단할 수 있습니다. 이미지를 내 도메인에서만 허용하는 엄격한 정책은 삽입된 이미지를 거부하고 사진이 나타나지 않습니다.

사이트가 엄격한 정책을 쓴다면 img-src 지시문에 data:를 허용하거나 이미지를 파일로 링크하세요. 정책 결정은 성능 논의가 아니라 보안팀의 몫입니다.

삽입된 이미지는 간단한 감사에서 내용도 숨깁니다. 코드를 훑어보는 검토자는 문자열을 디코딩하지 않고는 이미지가 무엇을 보여주는지 볼 수 없어 보안 검토가 어려워집니다.

사용자가 올린 이미지는 절대 맹목적으로 삽입하지 마세요. 먼저 디코딩해서 유효한 이미지인지 검증하세요. Base64 문자열은 이미지가 아닌 파일까지 포함해 어떤 파일이든 담을 수 있기 때문입니다.

아무도 세지 않는 유지 비용

삽입된 이미지는 코드 한가운데 있는 텍스트의 벽입니다. 파일을 읽기 어렵게 하고, 검토하기 어렵게 하고, 검색하기 어렵게 만듭니다. 문자열은 무엇을 묘사하는지 힌트를 주지 않기 때문입니다.

삽입된 이미지를 업데이트한다는 것은 문자열을 찾아 교체하고 올바른 것을 교체했길 바라는 것입니다. 링크된 파일은 업데이트가 파일 교체이고 코드는 절대 바뀌지 않습니다.

버전 관리도 문자열 때문에 힘들어집니다. 이미지에 대한 한 줄 변경이 코드 파일의 천 줄짜리 차이로 바뀌어, 실제 변경을 소음 속에 묻어버립니다.

반드시 삽입해야 한다면 삽입된 문자열을 별도의 파일이나 변수에 저장하세요. 주 코드가 읽기 쉽게 유지되고, 각 이미지를 따로 교체할 수 있습니다.

삽입 결정 체크리스트

삽입하기 전에 네 가지 질문을 하세요. 이미지가 10KB 미만인가요? 사이트 전체가 아니라 한 페이지나 몇 페이지에 나타나나요? 거의 바뀌지 않나요? 페이지가 단일 파일로 동작해야 하나요?

답이 전부 그렇다면 삽입하세요. 세 개가 그렇고 하나가 아니라면 신중히 생각하세요. 두 개 이상이 아니라면 이미지를 파일로 링크하세요.

API 페이로드와 이메일에서는 체크리스트가 다릅니다. 삽입이 선택이 아니라 필요할 수 있기 때문입니다. 그곳에서는 선택이 아니라 크기가 문제입니다. 먼저 압축한 뒤 삽입하세요.

사이트가 바뀌면 결정을 다시 살펴보세요. 랜딩 페이지에 삽입하는 게 맞았던 이미지가, 같은 페이지가 50페이지짜리 사이트의 일부가 되면 삽입이 틀릴 수 있습니다.

오래된 삽입 다시 살펴보기

삽입 결정은 시간이 지나면 나빠집니다. 단일 랜딩 페이지로 시작한 사이트가 50페이지로 자라고, 모든 페이지에 삽입된 로고는 아무도 만들었다는 걸 기억하지 못하는 캐싱 부담이 됩니다.

1년에 한 번 삽입을 감사하세요. 코드베이스에서 data:image가 나오는 곳을 검색하고, 크기를 나열하고, 각 항목이 이 글의 체크리스트 아래에서 여전히 자리를 차지할 자격이 있는지 물어보세요.

삽입을 다시 링크 파일로 옮기는 건 쉽습니다. 디코딩한 이미지를 저장하고, 업로드하고, 문자열을 URL로 교체하세요. 페이지가 가벼워지고, 이미지가 캐시되고, 코드가 다시 읽기 쉬워집니다.

반대 이동도 마찬가지로 유효합니다. 사이트가 클 때 링크됐던 작은 이미지는, 페이지가 독립 문서가 되면 삽입할 가치가 있을 수 있습니다. 원래 선택이 아니라 현재 용도가 결정하게 하세요.

빠른 참고: 삽입할까 링크할까

2KB 미만의 아이콘, 단일 페이지의 작은 로고, 단일 파일 문서와 이메일의 이미지를 삽입하세요. 아낀 요청이 더해진 바이트보다 가치가 큽니다.

사진, 사이트 전체의 로고, 50KB가 넘는 모든 것을 링크하세요. 캐시 절약과 렌더링 속도가 요청 절약을 큰 차이로 이깁니다.

API에서는 Base64가 표준이니 먼저 압축하고 작은 결과를 삽입하세요. 그 외의 모든 것은 페이지를 두 가지 방식으로 측정하고 숫자가 결정하게 하세요.

인코딩하려면 이미지 Base64 변환기를, 되돌리려면 Base64 이미지 디코더를 쓰세요. 전체 배경은 이미지 Base64 변환 완전 가이드와 단계별 설명인 이미지를 Base64로 변환하는 방법에서 확인하세요.

자주 묻는 질문

어느 파일 크기부터 Base64 이미지 삽입을 그만둬야 하나요?

흔한 규칙은 10KB입니다. 그 아래에서는 삽입이 보통 이기고, 50KB 위에서는 링크가 거의 항상 이깁니다. 그 사이에서는 캐싱 계산으로 경우마다 결정하세요. 50페이지에 있는 이미지는 5KB라도 링크해야 하고, 랜딩 페이지의 일회성 이미지는 30KB라도 삽입할 수 있습니다.

Base64 이미지를 삽입하면 SEO에 해가 되나요?

이미지 SEO에는 해가 될 수 있습니다. 삽입된 이미지는 링크된 파일처럼 인덱싱되거나 이미지 검색에 표시되지 않기 때문입니다. 페이지 SEO에 미치는 영향은 간접적입니다. 무거운 HTML은 더 느리게 로드되고, 느린 페이지는 순위가 더 낮습니다. 검색 엔진이 찾길 원하는 이미지는 링크하세요.

왜 어떤 개발자는 모든 아이콘을 Base64로 삽입하나요?

아이콘은 아주 작고 수가 많기 때문에, 삽입하면 아주 적은 바이트로 많은 요청을 아낄 수 있기 때문입니다. 1KB짜리 아이콘 열두 개를 삽입하면 총 약 16KB에 추가 요청이 0개입니다. 아이콘에는 이 관행이 맞지만, 사진이나 큰 그래픽에는 적용되지 않습니다.

Base64 삽입이 내 콘텐츠 보안 정책을 깨뜨릴 수 있나요?

네, 가능합니다. 특정 도메인에서만 이미지를 허용하는 엄격한 정책은 img-src 지시문에 data:가 명시적으로 허용되지 않는 한 Data URL을 차단합니다. 삽입하기 전에 정책을 확인하거나, 허용된 소스 안에 머무르도록 이미지를 파일로 링크하세요.

이미지를 삽입하는 것과 CSS 스프라이트를 쓰는 것 중 어느 것이 더 좋나요?

아이콘 세트에는 스프라이트나 SVG 심볼 시트가 보통 더 좋습니다. 한 번 캐시돼 모든 아이콘을 제공하기 때문입니다. 아이콘이 한두 개라면 삽입이 더 간단하고 차이는 무시할 만합니다. 아이콘 수가 몇 개를 넘어서면 스프라이트를 고르세요.

Base64 인코딩이 이미지 품질에 영향을 주나요?

아니요. 인코딩은 완전히 되돌릴 수 있고 픽셀을 전혀 바꾸지 않습니다. 품질 문제는 별개입니다. 삽입 뒤 이미지가 나빠 보인다면 문제는 원본 파일이나 인코딩 전에 적용된 압축이지 Base64 자체가 아닙니다.
