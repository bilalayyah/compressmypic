이미지 최적화와 Core Web Vitals: LCP와 파일 크기

이미지 최적화가 Core Web Vitals를 개선하는 방법입니다. LCP, CLS, INP가 무엇인지, 느린 페이지를 고치는 실전 방법, 압축과 리사이즈로 점수를 올리는 요령까지 정리했습니다. 바로 적용할 수 있는 방법 위주로 담았습니다.

Core Web Vitals는 구글이 페이지를 평가하는 데 쓰는 속도 점수입니다. 가장 큰 콘텐츠가 얼마나 빨리 나타나는지, 레이아웃이 얼마나 안정적인지, 페이지가 얼마나 빨리 반응하는지 측정합니다.

이미지는 세 가지 점수 모두에 영향을 줍니다. 무거운 대표 이미지는 가장 큰 화면 그리기를 늦추고, 너비가 빠진 이미지는 레이아웃 이동을 일으키며, 부풀어 오른 페이지는 상호 작용을 느리게 합니다.

이 글에서는 이미지 최적화가 각 점수를 어떻게 움직이는지, 느린 페이지에서 무엇을 먼저 고쳐야 하는지 설명합니다.

Core Web Vitals란?

Core Web Vitals는 페이지 로딩의 사용자 경험을 설명하는 세 가지 지표입니다. 실험실이 아니라 실제 방문자를 기준으로 측정됩니다.

최대 콘텐츠풀 페인트(LCP)는 눈에 보이는 가장 큰 요소가 나타나는 데 걸리는 시간을 측정합니다. 대부분 페이지에서 그 요소는 이미지입니다.

누적 레이아웃 이동(CLS)은 로딩 중 페이지가 얼마나 움직이는지 측정합니다. 픽셀 크기가 없는 이미지가 가장 흔한 원인입니다.

상호 작용 다음 페인트(INP)는 페이지가 클릭과 탭에 얼마나 빨리 반응하는지 측정합니다. 큰 이미지가 많은 무거운 페이지는 더 느리게 반응합니다.

구글은 이 점수를 검색 순위에 사용합니다. 빠른 페이지가 순위가 더 좋고, 이미지 최적화는 대부분 사이트가 가진 가장 큰 단일 방법입니다.

LCP: 대표 이미지가 결정하는 이유

LCP는 보통 대표 이미지가 결정합니다. 화면에서 가장 큰 요소이므로 대표 이미지가 나타날 때까지 페이지는 로딩된 것으로 간주되지 않습니다.

5MB 대표 이미지는 모바일 인터넷에서 다운로드하는 데 몇 초가 걸릴 수 있습니다. 그 몇 초 동안 방문자는 대표 이미지가 있어야 할 자리에 빈 공간을 봅니다.

대표 이미지를 수백 킬로바이트로 압축하면 대기 시간이 크게 줄어듭니다. 이미지가 더 빨리 나타나고 LCP 점수가 즉시 좋아집니다.

픽셀 크기도 중요합니다. 표시 크기보다 두 배로 제공되는 대표 이미지는 아무도 보지 않는 픽셀에 대역폭을 낭비해 화면 그리기를 더 늦춥니다.

대표 이미지를 미리 로딩하는 것도 도움이 됩니다. 가장 중요한 이미지를 브라우저에 일찍 알리면 다른 것보다 먼저 다운로드가 시작됩니다.

느린 LCP를 단계별로 고치기

첫째, LCP 요소를 찾으세요. 속도 측정 도구가 직접 알려주고, 보통 대표 이미지나 큰 배너입니다.

둘째, 웹 이미지 최적화 도구로 그 이미지를 최적화하세요. 대표 프리셋을 쓰면 크기를 정확히 맞추고 화질을 높게 유지합니다.

셋째, 대표 이미지의 지연 로딩이 꺼져 있는지 확인하세요. 가장 중요한 이미지를 늦추는 것이 가장 흔한 LCP 실수입니다.

넷째, 페이지 상단에서 대표 이미지를 미리 로딩하세요. 브라우저가 스타일시트나 스크립트와 대역폭을 겨루기 전에 먼저 가져옵니다.

다섯째, 페이지를 다시 테스트하세요. LCP 시간은 크게 떨어져야 하고, 모바일에서는 종종 몇 초가 줄어듭니다.

CLS: 이미지가 레이아웃을 이동시키는 방식

CLS는 예상치 못한 움직임을 측정합니다. 공간을 예약하지 않고 이미지가 늦게 열리면 아래 글자가 아래로 밀려 방문자가 읽던 위치를 잃습니다.

해결책은 간단합니다. 이미지 태그에 항상 너비와 높이를 포함하세요. 브라우저가 이미지가 도착하기 전에 공간을 예약합니다.

최적화 도구의 이미지 태그 복사 버튼은 이 픽셀 크기를 자동으로 포함합니다. 태그를 그대로 붙여넣으면 이동이 완전히 막힙니다.

화면 비율도 중요합니다. 예약된 공간에 비율이 잘못된 이미지가 들어가면 이동이 없어도 일그러져 깨진 것처럼 보입니다.

페이지를 새로 열고 움직임이 있는지 지켜보며 확인하세요. 보이는 모든 움직임은 점수를 해칠 CLS 문제입니다.

INP: 이미지 무게가 상호 작용을 늦추는 방식

INP는 반응 속도를 측정합니다. 방문자가 버튼을 누르면 페이지가 빨리 반응해야 하고, 무거운 페이지는 느리게 반응합니다.

이미지는 INP에 간접적으로 영향을 줍니다. 메가바이트 단위의 이미지가 있는 페이지는 브라우저가 다운로드하고 디코딩하느라 바빠 탭에 대한 반응이 늦어집니다.

지연 로딩이 여기서 도움이 됩니다. 화면 아래쪽 이미지는 페이지가 상호 작용 가능해지기 전에 다운로드할 필요가 없으므로 미루면 브라우저가 여유를 얻습니다.

큰 이미지를 디코딩하는 데도 시간이 듭니다. 너무 큰 이미지는 다운로드한 뒤에도 제대로 크기가 맞는 이미지보다 디코딩이 오래 걸립니다.

해결책은 LCP와 같습니다. 모든 이미지 크기를 맞추고, 화면 아래쪽 이미지는 지연 로딩하고, 전체 페이지 무게를 낮게 유지하세요.

Core Web Vitals 제대로 측정하기

빠른 사무실 인터넷뿐 아니라 실제 기기에서 측정하세요. 대부분 방문자는 휴대폰으로 둘러보고 모바일 점수가 중요합니다.

무료 속도 측정 도구로 기준선을 잡으세요. 변경하기 전에 LCP, CLS, INP 숫자를 적어두세요.

한 번에 한 가지만 바꾸세요. 대표 이미지를 최적화한 뒤 다시 테스트하면 대표 이미지가 얼마나 비용이 들었는지 정확히 알 수 있습니다.

각 수정 뒤 다시 테스트하세요. 점수는 단계적으로 움직이고, 각 단계가 마지막 변경이 도움이 됐는지 보여줍니다.

점수는 방문자마다 다르다는 점을 기억하세요. 한 번의 테스트는 스냅샷이고, 며칠에 걸친 여러 번의 테스트가 진짜 모습을 보여줍니다.

페이지의 이미지 예산 정하기

이미지 예산은 페이지 이미지의 전체 무게를 제한합니다. 흔한 예산은 콘텐츠 페이지 1MB, 갤러리 2MB입니다.

예산을 이미지 수로 나누세요. 1MB 예산을 공유하는 이미지 10장은 각각 100KB를 받아 합리적인 목표가 됩니다.

대표 이미지에는 더 큰 몫을 주세요. 300KB나 400KB가 맞고 보조 이미지는 각각 100KB를 받습니다.

게시 과정에서 예산을 지키세요. 이미지 무게를 포함하는 체크리스트는 무거운 이미지가 공개 사이트에 도달하는 것을 막습니다.

디자인이 바뀔 때 예산을 검토하세요. 이미지가 더 커진 새 테마는 더 큰 예산이 필요하거나 크기에 맞는 더 작은 이미지가 필요합니다.

포맷과 Core Web Vitals

WebP는 Core Web Vitals에 가장 좋은 포맷입니다. 같은 화질에서 JPG보다 작아 LCP에 직접 도움이 됩니다.

최신 브라우저는 모두 WebP를 지원합니다. 이 포맷은 주류 사이트에 더 이상 위험이 아니고 속도 향상은 분명합니다.

JPG는 오래된 시스템용 대체 포맷으로 남습니다. 속도보다 호환성이 중요할 때는 JPG가 안전한 선택입니다.

PNG은 사진에서 Core Web Vitals를 해칩니다. 큰 파일이 LCP를 늦추고 페이지를 부풀리므로 PNG은 그래픽에만 쓰세요.

방문자의 브라우저가 지원하는 가장 작은 포맷을 제공하세요. 이 하나의 규칙이 포맷 혜택의 대부분을 차지합니다.

반응형 이미지와 해상도 전환

반응형 이미지는 화면마다 다른 크기를 제공합니다. 휴대폰은 작은 파일을 받고 데스크톱은 큰 파일을 받습니다.

HTML srcset 속성은 사용 가능한 크기를 나열하고 브라우저가 실행되는 화면에 맞는 크기를 고릅니다.

이는 모바일 LCP에 중요합니다. 데스크톱 크기 대표 이미지를 다운로드하는 휴대폰은 작은 화면이 보여줄 수 없는 픽셀에 몇 초를 낭비합니다.

이미지마다 두세 가지 크기를 만드세요. 모바일 크기, 태블릿 크기, 데스크톱 크기입니다. 최적화 도구의 프리셋은 각 크기를 한 번 클릭으로 만듭니다.

반응형 이미지를 추가한 뒤 실제 휴대폰에서 테스트하세요. 모바일의 LCP 개선은 종종 극적입니다.

흔한 Core Web Vitals 실수

대표 이미지를 지연 로딩하는 것이 가장 흔한 실수입니다. LCP 요소를 늦춰 나쁜 점수를 보장합니다.

너비와 높이가 빠진 것이 두 번째입니다. 픽셀 크기가 없는 이미지는 레이아웃을 이동시켜 CLS 점수를 해칩니다.

너무 큰 이미지를 제공하는 것이 세 번째입니다. 800픽셀로 표시되는 4000픽셀 이미지는 대역폭을 낭비하고 화면 그리기를 늦춥니다.

화면 아래쪽 이미지를 잊는 것이 네 번째입니다. 대표 이미지가 빠른 페이지도 뒤따르는 최적화되지 않은 썸네일 20장 때문에 전체적으로 느릴 수 있습니다.

이 네 가지 실수를 고치면 이미지 관련 Core Web Vitals 문제 대부분이 해결됩니다. 간단하고 효과 있습니다.

먼저 고칠 것: 우선순위

LCP 이미지를 먼저 고치세요. 점수와 방문자의 첫인상에 가장 큰 단일 효과를 줍니다.

빠진 픽셀 크기를 두 번째로 고치세요. 모든 이미지 태그에 너비와 높이를 추가하면 빠르고 레이아웃 이동이 사라집니다.

전체 무게를 세 번째로 고치세요. 화면 아래쪽 이미지를 지연 로딩하고 나머지를 압축해 페이지를 예산 아래로 가져오세요.

반응형 이미지를 네 번째로 고치세요. 반응형 이미지는 모바일 방문자에게 가장 도움이 되고 모바일 점수가 가장 중요합니다.

각 단계 뒤 다시 테스트하세요. 점수는 페이지가 충분히 좋은지, 더 작업이 필요한지 알려줍니다.

현장 데이터 vs 실험실 데이터

Core Web Vitals는 두 종류가 있습니다. 한 번의 테스트에서 나오는 실험실 데이터와 수주에 걸친 실제 방문자의 현장 데이터입니다.

실험실 데이터는 즉시 나오고 반복 가능합니다. 통제된 테스트에서 빠른 인터넷 환경의 페이지 성능을 알려줍니다.

현장 데이터는 느리지만 정직합니다. 느린 인터넷을 포함해 실제 휴대폰과 실제 인터넷 환경의 실제 방문자를 반영합니다.

구글은 현장 데이터로 순위를 매깁니다. 실험실에서는 점수가 좋지만 현장에서 나쁜 페이지는 여전히 순위가 나쁩니다.

실험실 데이터로 문제를 찾고 현장 데이터로 수정 사항을 확인하세요. 둘을 함께 쓰면 페이지 속도의 전체 모습을 볼 수 있습니다.

LCP 요소가 이미지가 아닐 때

가끔 가장 큰 화면 그리기가 이미지가 아니라 글자 블록입니다. 이럴 때는 이미지 최적화의 도움이 적고 글꼴과 스타일시트가 더 중요합니다.

속도 측정 도구가 LCP 요소로 무엇을 지목하는지 확인하세요. 글자라면 글꼴 로딩과 렌더링을 막는 스타일을 살펴보세요.

이미지도 글자 LCP를 늦출 수 있습니다. 무거운 배경 이미지나 느리게 열리는 로고가 페이지 전체를 붙잡을 수 있습니다.

이미지는 그래도 최적화하세요. 가벼운 페이지는 LCP 요소 자체가 글자여도 모든 지표에 도움이 됩니다.

맹목적으로 최적화하지 마세요. 어떤 요소가 점수를 이끄는지 알면 노력을 어디에 쓸지 알 수 있습니다.

이미지 너머의 CLS: 글꼴과 광고

이미지는 가장 흔한 CLS 원인이지만 유일한 원인은 아닙니다. 웹 글꼴과 광고도 로딩하면서 레이아웃을 이동시킵니다.

글꼴은 교체되면서 글자를 이동시킵니다. font-display swap과 비슷한 대체 글꼴을 쓰면 보이는 움직임을 줄일 수 있습니다.

광고는 늦게 열리면서 콘텐츠를 이동시킵니다. 광고 자리에 공간을 예약하면 광고가 도착할 때 페이지가 움직이는 것을 막습니다.

이미지를 먼저 고치세요. 가장 쉬운 성과이기 때문입니다. CLS 점수가 여전히 나쁘면 글꼴과 광고를 살펴보세요.

레이아웃 이동이 없는 페이지는 차분하고 전문적으로 느껴집니다. 방문자는 이름을 붙일 수 없어도 안정감을 알아챕니다.

INP와 무거운 스크립트

이미지는 INP 문제의 주된 원인이 거의 아닙니다. 무거운 자바스크립트가 느린 상호 작용의 더 큰 원인인 경우가 많습니다.

그래도 이미지 작업이 INP에 도움이 됩니다. 가벼운 페이지는 브라우저가 탭과 클릭에 반응할 시간을 더 남깁니다.

디코딩 비용도 중요합니다. 너무 큰 이미지는 제대로 크기가 맞는 이미지보다 디코딩이 오래 걸리고, 디코딩은 상호 작용을 막습니다.

서드파티 스크립트는 가볍게 유지하세요. 분석, 채팅 위젯, 소셜 임베드는 모두 브라우저의 관심을 두고 내 페이지와 겨룹니다.

INP를 예산이라고 생각하세요. 모든 스크립트와 이미지가 예산을 쓰고, 페이지는 예산이 다하기 전에 반응해야 합니다.

모바일 우선: 휴대폰 점수가 가장 중요한 이유

대부분 방문자는 휴대폰으로 둘러보고 구글은 모바일 점수로 순위를 매깁니다. 데스크톱에서는 빠르지만 모바일에서는 느린 페이지는 순위가 나쁩니다.

휴대폰은 인터넷이 느리고 프로세서가 약합니다. 같은 대표 이미지도 노트북보다 휴대폰에서 다운로드하고 디코딩하는 데 더 오래 걸립니다.

휴대폰용으로 먼저 최적화하세요. 모바일에서 빠른 페이지는 어디서나 빠르고, 반대는 그렇지 않습니다.

데스크톱 시뮬레이터가 아니라 실제 휴대폰에서 테스트하세요. 시뮬레이터는 방문자가 실제로 느끼는 현실의 느림을 숨깁니다.

모바일 우선 최적화는 유행이 아닙니다. 지금 웹이 동작하는 방식이고 점수가 이를 반영합니다.

Core Web Vitals 계속 지켜보기

Core Web Vitals는 시간이 지나면서 바뀝니다. 새 이미지, 새 플러그인, 새 테마가 모두 조용히 점수를 해칠 수 있습니다.

최소 한 달에 한 번 점수를 확인하세요. 정기적인 확인은 순위에 영향을 주기 전에 문제를 잡아냅니다.

플랫폼이 지원하면 알림을 설정하세요. LCP가 기준을 넘을 때 알림이 오면 느린 순위 몇 주를 아껴줍니다.

디자인을 바꿀 때마다 점수를 검토하세요. 새 테마는 모든 이미지 자리를 바꾸고 이전 최적화가 더 이상 맞지 않을 수 있습니다.

속도는 습관이지 프로젝트가 아닙니다. 계속 지켜보는 사이트가 빠른 상태를 유지합니다.

게시 전 최종 확인

모든 수정을 마친 뒤 속도 측정 도구를 마지막으로 실행하세요. LCP, CLS, INP가 모두 녹색 범위 안에 있는지 확인한 뒤 다음으로 넘어가세요.

모바일 인터넷으로 실제 휴대폰에서 페이지를 여세요. 실험실 테스트의 숫자는 유용하지만 휴대폰에서의 느낌이 진실입니다.

전체 최적화 도구 가이드는 웹 이미지 최적화 완벽 가이드에서 확인하세요. 실전 단계는 웹사이트 속도용 이미지 최적화 방법을 참고하세요. 간단한 크기 목표에는 200KB 압축기와 대량 이미지 압축기가 무거운 작업을 처리합니다.

자주 묻는 질문

좋은 LCP 점수는 어느 정도인가요?

구글은 LCP 2.5초 미만을 좋은 점수로 봅니다. 대부분 페이지는 무거운 대표 이미지 때문에 이 기준에 못 미칩니다. 대표 이미지를 압축하고 올바른 크기로 제공하며 미리 로딩하는 것이 기준 아래로 들어가는 가장 빠른 방법입니다.

이미지가 레이아웃 이동을 일으키는 이유는 무엇인가요?

너비와 높이 속성이 없는 이미지가 열리면 브라우저는 얼마나 공간을 예약해야 할지 모릅니다. 이미지가 늦게 도착해 아래 콘텐츠를 아래로 밀어내는데, 이것이 레이아웃 이동으로 측정됩니다. 태그에 픽셀 크기를 포함하면 막을 수 있습니다.

지연 로딩이 Core Web Vitals를 개선하나요?

네, 화면 아래쪽 이미지에 한해서는 개선합니다. 미루면 대표 이미지용 대역폭이 확보되고 페이지가 더 빨리 상호 작용 가능해집니다. 대표 이미지나 로고는 절대 지연 로딩하지 마세요. 늦추면 LCP가 직접 해칩니다.

모바일 LCP 점수가 데스크톱보다 나쁜 이유는 무엇인가요?

모바일 인터넷은 느리고 휴대폰 프로세서는 약해서 같은 대표 이미지도 다운로드하고 디코딩하는 데 더 오래 걸립니다. 대표 이미지를 최적화하고 모바일용으로 더 작은 버전을 제공하며 미리 로딩하면 격차 대부분이 줄어듭니다.

이미지 최적화만으로 나쁜 Core Web Vitals 점수를 고칠 수 있나요?

이미지가 주된 문제라면 종종 네, 가능합니다. 이미지 5MB인 페이지는 최적화하면 극적으로 좋아집니다. 점수가 여전히 나쁘면 느린 호스팅, 무거운 스크립트, 렌더링을 막는 스타일시트가 문제일 수 있습니다.

Core Web Vitals를 얼마나 자주 다시 확인해야 하나요?

디자인을 바꿀 때마다, 최소 한 달에 한 번 확인하세요. 새 이미지, 새 테마, 새 플러그인이 모두 조용히 점수를 해칠 수 있습니다. 한 달에 한 번 확인하면 순위에 영향을 주기 전에 문제를 잡을 수 있습니다.
