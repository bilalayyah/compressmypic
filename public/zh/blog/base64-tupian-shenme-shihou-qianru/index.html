Base64 图片：什么时候该嵌入、什么时候不该

嵌入Base64图片能省请求，却要多花33%的字节，还无法单独缓存。了解大小阈值、缓存取舍和决策清单，看懂什么时候嵌进代码更划算，什么时候老老实实用图片链接更好。还给了一个决策清单，讲清多大的图片值得嵌入、多大的应该用链接，以及缓存和加载速度怎么权衡。

把图片嵌为 Base64 感觉像白捡的好处。少一次请求，不用管理单独的文件，图片在页面加载的那一刻就出现。

这个好处是真实的，但不是免费的。嵌入的图片要多花三分之一的字节，无法单独缓存，还会让代码更难读、更难维护。

本文会给你一个决策框架：大小阈值、缓存计算，以及哪些情况下嵌入有帮助、哪些情况下会起反作用。

一句话说清嵌入决策

图片小、关键、稳定时，嵌入它。一个每个页面都需要、很少变化、单独获取要花一次请求的小图标，就是完美的候选。

图片大、共享、常变时，链接它。一张照片、五十个页面共用的 Logo，或者每周更新的图片，应该作为浏览器可以缓存的文件存在。

大多数图片都明显属于其中一边。麻烦的是中间那些情况，本文剩下的部分就是讲如何判断它们。

拿不准的时候，测量一下。下面的阈值能给你数字做判断依据，而不是凭感觉。

大小阈值：具体数字

2 KB 以下，不用想，直接嵌入。膨胀不到一 KB，省下的请求价值远远超过这点代价，没有任何用户会注意到成本。

2 KB 到 10 KB 之间，嵌入通常还是对的。膨胀最多几 KB，图片小到缓存几乎不重要。

10 KB 到 50 KB 之间，要根据具体情况逐个判断。首屏上方的关键图标可能值得，但某个页面上的装饰图片可能不值得。

50 KB 以上，链接几乎总是更好。光是膨胀就有 16 KB 或更多，而浏览器本来可以缓存这个文件，在各个页面复用。

缓存取舍

缓存是嵌入隐藏的成本。链接的图片下载一次，每个引用它的页面都能复用，缓存头允许多久就复用多久；而嵌入的图片，每个包含它的页面都要重新下载一次。

想想一个五十页网站上的 10 KB Logo。链接的话，一次花 10 KB；嵌入的话，每个页面花 13 KB，完整访问一遍就是 650 KB。

单页访问时，这个计算会反过来。只读一个页面的访客只需付一次嵌入成本，省下的请求可能让页面比链接版本更快。

做决定之前，先了解你的流量模式。访问深入的博客应该链接共享图片，只有一页的落地页则可以自由嵌入。

请求与字节：哪个代价更大

每个图片请求都要往返服务器一次，还要加上连接的开销。在快速连接上，这个成本很小，但在慢速移动连接上，它可能主导加载时间。

嵌入能完全消除往返。图片随 HTML 一起到达，没有额外的等待、没有额外的连接，也没有请求失败的风险。

但嵌入会给 HTML 本身增加字节，而 HTML 是阻塞渲染的。一个嵌了一 MB 图片的页面，必须先下载全部内容才能显示任何东西；链接图片的页面可以先渲染文字，再陆续填入图片。

这些年平衡点已经移动了。有了 HTTP/2 和 HTTP/3，请求的成本比过去低了，所以除了最小的图片，嵌入的理由已经变弱了。

图标和 Logo：嵌入

图标是最适合嵌入的候选。它们很小，通常不到 2 KB，一个页面可能需要十几个，链接的话就是十几个请求。

雪碧图或图标字体可以替代图标集的嵌入，两者都值得考虑。但页面上只有一两个图标时，Data URL 更简单、实现更快。

Logo 的情况更接近边界。一个 10 KB 以下、出现在每个页面上的小 Logo，嵌入时会损失缓存；但单落地页上的 Logo，嵌入是没问题的。

全站使用的 Logo，链接它。浏览器缓存一次，之后的每个页面加载都更快，因为 Logo 已经在那里了。

照片：不要嵌入

照片几乎永远不应该嵌入。一张典型的网页照片是 100 KB 到 500 KB，变成字符串后是 130 KB 到 670 KB，这些重量都塞在 HTML 里面。

HTML 膨胀会延迟渲染，因为浏览器必须先下载整个文档才能显示任何内容。链接照片的页面会先渲染文字，再陆续填入照片。

照片的更换频率也比图标高。每次换照片，都要编辑包含字符串的代码，容易出错，也很难审查。

唯一的例外是必须离线工作的单文件文档。一份带一张嵌入照片的报告或邮件可以接受，因为没有其他办法让图片出现。

CSS 背景与图案

CSS 里的小重复图案和纹理是很好的嵌入候选。一张 2 KB 的平铺图在背景上重复出现，成本很小，每个使用该样式表的页面都能省一次请求。

装饰渐变和形状更适合用纯 CSS 实现，完全不用图片。CSS 写的渐变只要几十个字符，还能完美缩放。

大背景照片应该保持链接。一张 200 KB 的主视觉背景嵌进样式表会变成 270 KB，而样式表是阻塞渲染的，整个页面都要等它。

当背景图片嵌在 CSS 里时，它无法和样式表分开缓存。改一行 CSS，浏览器就必须把每个嵌入的图片和它一起重新下载。

HTML 邮件：小的嵌入，大的链接

邮件是嵌入常常是必需而不是可选项的唯一场景。很多客户端默认屏蔽远程图片，所以链接的图片可能永远不出现。

嵌入 Logo 和让消息一眼可识别的小装饰图片。这些是邮件看起来正确所必须的图片。

大照片改用链接，或者完全不放。重的嵌入照片会让消息在手机上打开很慢，有些客户端还会拒绝超过大小限制的消息。

在你的受众使用的客户端里测试。有些会屏蔽内联 Base64 图片，这会把整个计算反转，让托管图片成为对这部分受众更安全的选择。

API 数据：Base64 是标准

API 是和网页完全不同的世界。JSON 无法承载二进制数据，所以在 JSON 数据里传输的图片必须是 Base64，这里没有链接的替代方案。

这里的决定不是嵌入还是链接，而是图片到底该不该放进请求体。小头像或签名图片放进去没问题，而几 MB 的照片可能值得一个专门的上传接口。

留意请求体大小限制。很多 API 把请求上限设在几 MB，一张 2 MB 的照片变成 2.7 MB 的字符串，自己就能超出上限。

API 使用时，先压缩再编码。编码之前把照片减到 200 KB，生成的字段是 270 KB，几乎任何请求体上限都能轻松容纳。

测量真实的性能影响

关于嵌入的观点很廉价，所以要测量。先加载链接图片的页面，记下时间，再加载嵌入图片的页面，对比一下。

要在慢速移动连接上测试，不只是在快速的办公室 Wi-Fi 上。省请求的好处在慢速网络上最明显，字节成本在同样的网络上也最明显，所以不测试，平衡点真的不清楚。

检查两个版本的页面总重量。嵌入的页面因为 33% 的膨胀而更重，这份重量会在每次性能审计里出现。

也要检查重复访问。第一次访问可能偏向嵌入，第二次访问偏向链接，因为缓存的图片第二次是免费的。

Base64 嵌入的替代方案

SVG 图片有更便宜的选择：URL 编码的 SVG。直接写进 Data URL 的小 SVG 不用 Base64，完全跳过 33% 的膨胀，所以更短。

图标字体和 SVG 雪碧图能用一个缓存文件替代很多小嵌入图片。它们花一次请求，然后从缓存里为全站提供每个图标。

HTTP/2 服务器推送和预加载提示能让链接图片几乎和嵌入一样快。浏览器提前获取图片，请求成本趋近于零。

对经常变化的图片来说，带积极缓存的内容分发网络能彻底击败嵌入。第一次访问很快，之后的每次访问几乎免费。

安全与内容安全策略

内容安全策略（CSP）头可能会屏蔽 Data URL。只允许图片来自你自己域名的严格策略会拒绝嵌入的图片，图片就不会显示。

如果你的网站使用严格策略，要么在图片源指令里允许 data:，要么把图片链接为文件。策略决定属于你的安全团队，不属于性能讨论。

嵌入的图片还会让简单审计看不到内容。审查代码的人不解码字符串就看不到图片画的是什么，这让安全审查更难。

对用户上传的图片，千万不要盲目嵌入。先解码并验证图片，因为 Base64 字符串可以承载任何文件，包括根本不是图片的东西。

没人计算的维护成本

嵌入的图片是代码中间的一堵文字墙。它让文件更难读、更难审查、更难搜索，因为字符串本身没有任何关于它画了什么的提示。

更新嵌入的图片意味着找到字符串、替换它，并祈祷自己替换的是正确的那一个。用链接文件更新时，只需替换文件，代码永远不用变。

版本控制也会受影响。图片的一行改动会变成代码文件里上千行的 diff，把真正的改动淹没在噪音里。

必须嵌入时，把嵌入的字符串存在单独的文件或变量里。这样主代码保持可读，每个图片也能单独替换。

嵌入决策清单

嵌入之前问四个问题。图片在 10 KB 以下吗？它出现在一个或少数几个页面上，而不是全站吗？它很少变化吗？页面必须作为单个文件工作吗？

如果答案都是「是」，嵌入它。如果三个是、一个否，仔细想想。如果两个或更多是否，把图片链接为文件。

对 API 数据和邮件来说，清单不一样，因为嵌入可能是必需而不是可选项。那里的问题是大小，而不是选择：先压缩，再嵌入。

网站变化时，重新审视这个决定。落地页上嵌入正确的图片，一旦同一个页面变成五十页网站的一部分，嵌入可能就错了。

重新审视旧的嵌入

嵌入决策老化得很快。一个从单落地页起步的网站长成五十页，嵌在每个页面上的 Logo 就变成了一个缓存负担，而没人记得是谁创建的。

每年审计一次嵌入。在代码库里搜索 data:image，列出大小，按本文清单逐个问它是否还值得留在那里。

把嵌入改回链接文件很容易：解码字符串保存图片，上传它，用 URL 替换字符串。页面变轻了，图片被缓存了，代码也变可读了。

反向操作同样合理。网站很大时链接的小图片，当页面变成独立文档时可能值得嵌入。让当前的用途决定，而不是最初的选择。

快速参考：嵌入还是链接

2 KB 以下的图标、单页面上的小 Logo、单文件文档和邮件里的图片，嵌入它们。省下的请求比增加的字节更值得。

照片、全站 Logo，以及 50 KB 以上的任何内容，链接它们。缓存节省和渲染速度比省请求的收益大得多。

API 用 Base64 是标准，所以先压缩再嵌入小的结果。其他所有情况，两种方式都测一下页面，让数字来决定。

常见问题

文件多大就应该停止嵌入 Base64 图片？

常见的规则是 10 KB：低于这个值，嵌入通常更划算；高于 50 KB，链接几乎总是更划算。两者之间要结合缓存计算逐个判断。五十个页面上的图片即使只有 5 KB 也应该链接，而落地页上的一次性图片即使 30 KB 也可以嵌入。

嵌入 Base64 图片会伤害 SEO 吗？

可能伤害图片 SEO，因为嵌入的图片不会像链接文件那样被索引或出现在图片搜索里。对页面 SEO 的影响是间接的：更重的 HTML 加载更慢，加载慢的页面排名更差。希望搜索引擎找到的图片，用链接。

为什么有些开发者把所有图标都嵌为 Base64？

因为图标又小又多，嵌入能省很多请求，只花很少字节。十几个 1 KB 的图标嵌入后总共大约 16 KB，零额外请求。这种做法对图标是合理的，但不适用于照片或大图形。

Base64 嵌入会破坏我的内容安全策略吗？

会。只允许图片来自特定域名的严格策略会屏蔽 Data URL，除非在 img-src 指令里明确允许 data:。嵌入之前先检查你的策略，或者把图片链接为文件，留在允许的来源之内。

嵌入图片好，还是用 CSS 雪碧图好？

对一组图标来说，雪碧图或 SVG 符号表通常更好，因为它缓存一次就能服务所有图标。对一两个图标来说，嵌入更简单，差别可以忽略。图标数量超过几个时，选雪碧图。

Base64 编码会影响图片质量吗？

不会。编码完全可逆，不改变任何像素。质量问题是另一回事：如果嵌入之后图片看起来很差，问题出在源文件或编码之前做的压缩，而不是 Base64 本身。
