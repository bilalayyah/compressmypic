Base64 与图片文件对比：性能与使用场景

Base64字符串和图片文件用不同方式承载同一张图片。对比大小、速度、缓存与编辑，了解各自在什么时候更胜一筹，选对承载方式，网页加载和小图标处理都更顺手。还按小图标、大图和可编辑图片分了场景，讲清哪种承载方式更省请求、哪种更利于缓存和修改。很容易上手。

网页上的每张图片都以两种形式之一存在：一个有名字和 URL 的文件，或者一段嵌在代码里的 Base64 字符串。两者承载的像素相同，行为却大不相同。

选错形式会损失性能、浪费带宽，或者把一次简单的更新变成痛苦的差事。选对形式，主要在于知道各自擅长什么。

本文会把 Base64 字符串和图片文件正面对比：大小、速度、缓存、编辑，以及各自明显胜出的使用场景。

存储同一张图片的两种方式

图片文件是有名字、格式和位置的二进制数据。浏览器用一次请求获取它，缓存它，每当页面引用它时就渲染它。

Base64 字符串是同样的二进制数据重写为文本。它存在于 HTML、CSS、JSON 或数据库里，浏览器当场解码，不用任何请求。

两种形式的像素完全相同。PNG 文件和它的 Base64 字符串解码后是同样的字节、同样的尺寸、同样的画面。

其他一切都不同：大小、速度、缓存、编辑和工具。这些差异正是这次对比的内容。

大小：33% 的差距

Base64 字符串比它编码的文件大约 33%。一张 90 KB 的图片会变成 120 KB 的字符串，一张 1 MB 的照片会变成 1.4 MB 的字符串。

这个差距是编码的固定属性。四个文本字符承载三个字节的数据，所以字符串需要的字符永远比文件的字节多三分之一。

对小图片来说，这个差距可以忽略。一张 3 KB 的图标变成 4 KB 的字符串，没人会去测量一 KB。对大图片来说，这个差距主导了决策。

文件大小对存储也很重要。装满 Base64 图片的数据库比同样图片以文件形式存储时大三分之一，每次备份都要重复这个成本。

性能：加载速度

链接的图片文件要花一次请求，但能渐进渲染。浏览器先显示文字，图片到了再填进去，所以即使在慢速连接上，页面感觉也很快。

嵌入的 Base64 图片不用请求，但会阻塞渲染。浏览器必须先下载整个 HTML 文档，包括字符串，才能显示任何内容。

只有一个小图标的页面，嵌入更快。省下的请求超过了额外的字节，图标随第一次绘制一起出现。

有很多或很大图片的页面，链接更快。文字立即渲染，图片陆续流入，浏览器还能优先处理读者先看到的内容。

缓存：决定性的区别

缓存是图片文件决定性胜出的地方。链接的文件下载一次，每个引用它的页面都能复用，缓存头允许多久就复用多久。

Base64 字符串每个包含它的页面都要重新下载一次。嵌在五十个页面上的 Logo 要下载五十次，而同一个 Logo 链接的话只需要下载一次。

这是共享图片优先用文件的最大原因。33% 的膨胀是一次性成本，缓存损失却在每次页面浏览时重复。

对单页文档、邮件和离线文件来说，缓存不适用，这个论点也就消失了。这正是嵌入在这些场景里成为标准做法的原因。

便携性：到处移动图片

Base64 字符串存在于文本里，这让它在文件做不到的地方也能移动。字符串可以粘贴进聊天消息、存在数据库行里，或者嵌进 JSON 数据。

图片文件需要一个位置：URL、文件夹或附件。移动文件意味着引用也要跟着移动，引用断了，图片就损坏了。

API 是字符串最明确的用例。JSON 无法承载二进制数据，所以任何在 JSON 数据里传输的图片都必须是 Base64，没有基于文件的替代方案。

对网站来说，文件在实际使用中更便携。一个文件可以被任何页面、任何样式表、任何邮件引用，而字符串必须分别复制进每个地方。

编辑与版本控制

更新链接的图片就是替换文件。替换文件、保留名字，每个引用它的页面都会立即显示新版本。

更新嵌入的图片意味着找到字符串、替换一堵文字，并祈祷自己替换的是正确的那一个。逻辑没变，代码却变了。

版本控制在字符串面前也很痛苦。图片的一行改动会变成上千行的 diff，淹没真正的代码改动，让审查很痛苦。

文件版本管理得很干净。图片变了就是一个二进制文件变了，diff 只有一行，历史记录能精确显示图片什么时候变了、替换了什么。

搜索、无障碍与分享

搜索引擎会索引链接的图片文件，并在图片搜索里展示它们。嵌入的 Base64 图片对这个系统基本不可见，所以不会带来任何图片搜索流量。

屏幕阅读器和无障碍工具两种形式都能处理，但前提是标记正确。图片元素无论源是文件还是字符串，都需要 alt 属性。

读者可以右键点击链接的图片，保存它、分享它，或在新标签页里打开它。大多数浏览器里，嵌入的图片也有同样的菜单，但保存下来的文件是生成的名字，没有任何上下文。

社交分享预览也更喜欢文件。依赖嵌入图片的页面在分享时可能没有预览缩略图，因为分享爬虫很难提取出一个。

API 与数据传输

接受 JSON 的 API 要求图片以 Base64 字符串的形式出现，因为 JSON 没有二进制类型。字符串放在一个字段里传输，服务器解码它，在另一端重建文件。

分段上传是基于文件的替代方案，对大图片更高效。分段请求直接发送二进制数据，没有 33% 的膨胀。

JSON 流程里的小图片，比如头像、签名和缩略图，选 Base64。大图片选分段上传，那里的膨胀会以 MB 来计算。

数据库遵循同样的逻辑。存为文本的小图片很方便，大图片属于对象存储，数据库里放一个引用就行。

邮件：小的字符串胜，大的文件胜

邮件是单独的消息，所以嵌入的图片会随文字一起传输，读者离线时也能显示。这比可能被屏蔽的链接图片有真正的优势。

小图片在邮件里嵌入效果很好：10 KB 以下的 Logo、图标和小横幅。它们让消息一打开就一眼可识别。

大照片应该保持链接，或者完全不放。重的嵌入照片会让消息在手机上打开很慢，有些邮件服务器还会拒绝超过大小限制的消息。

在你的受众使用的客户端里测试。有些会完全屏蔽内联 Base64 图片，这让整个嵌入的努力对那些读者毫无意义。

安全考虑

Base64 字符串会把内容藏起来，不让人在粗略检查时看到。审查代码的人不解码字符串就看不到图片画的是什么，这让安全审查更难。

内容安全策略头可能会屏蔽 Data URL。只允许图片来自你自己域名的严格策略会拒绝嵌入的图片，除非明确允许 data:。

图片文件更容易审计。文件可以被扫描、哈希、对照已知内容清单检查，而字符串在做这些之前必须先解码。

千万不要解码来自不可信来源的字符串，然后盲目地提供结果。存储或显示之前，先验证解码后的字节确实是一张真实图片。

图片文件明显胜出的情况

照片、全站 Logo，以及 50 KB 以上的任何内容，图片文件胜出。缓存节省和渲染速度比省请求的收益大得多。

经常变化的图片，文件胜出。替换文件能一次更新所有引用，而更新字符串意味着编辑每个包含嵌入副本的文件。

需要被找到的图片，文件胜出。搜索引擎、社交预览和图片搜索在链接文件上的表现都比嵌入字符串好。

团队协作，文件胜出。设计师不用碰代码就能替换文件，开发者能干净地审查改动，版本历史保持可读。

Base64 字符串明显胜出的情况

必须离线工作的单文件文档，字符串胜出。HTML 报告、保存的网页或邮件无法获取外部文件，嵌入是唯一的选择。

2 KB 以下的小图标，字符串胜出。膨胀不到一 KB，省下的请求是真实的，缓存损失对这么小的图片可以忽略。

JSON 数据和数据库字段，字符串胜出。基于文本的系统无法承载二进制数据，所以 Base64 是让图片通过它们的标准方式。

没有归宿的生成图片，字符串胜出。脚本实时创建的图片可以立即嵌入，不用先保存到服务器再取回一个 URL。

混合方案

大多数真实项目两种形式都用。小图标嵌入，照片链接，API 数据承载 Base64，网站提供文件。

混合规则很简单：小的、关键的嵌入，大的、共享的链接，任何基于文本的传输用字符串。

按图片类型而不是按单张图片记录选择。一条「5 KB 以下的图标嵌入，其他全部链接」的规则容易遵守，也容易审计。

项目变化时，重新审视这条规则。落地页长成完整网站后，嵌入的 Logo 可能需要改回链接文件。

两种形式之间的迁移

从字符串迁移到文件很直接。用Base64 转图片工具解码字符串，保存文件，上传它，用 URL 替换字符串。

从文件迁移到字符串同样容易。用图片转 Base64 工具编码文件，复制输出，粘贴到原来放 URL 的地方。

一次迁移一种图片类型，迁移前后都测量。让网站变慢的迁移是值得撤销的迁移。

迁移期间保留原始文件。解码后的文件和它的源字符串在新版本测试确认之前应该同时存在。

成本：带宽与存储

带宽是 Base64 选择最具体的成本。一个嵌了 1 MB 图片的页面要传输大约 1.33 MB 的图片数据，而同样的图片链接传输 1 MB，这个差别在每次页面浏览时都会重复。

在按流量计费的移动连接上，多出来的三分之一对读者来说是真金白银。大量嵌入的网站会让手机访客的数据成本明显高于同样的网站用链接图片。

存储遵循同样的比例。存了 10 GB 图片的数据库如果用 Base64 存储，实际是 13.3 GB 的文本，每次备份、复制和迁移都要承担额外的重量。

对象存储比数据库存储图片更便宜，这也是大图片属于文件的另一个原因。数据库里的引用只要几十个字符，图片本身住在存储便宜的地方。

计算是最小的成本。编码和解码都是快速操作，CPU 时间和网络、存储成本相比可以忽略，所以性能讨论应该关注字节，而不是周期。

估算嵌入的成本时，要乘以页面浏览量。一次访问看起来微不足道的 100 KB 膨胀，在十万次访问里会变成 10 GB 的额外传输。

快速参考：字符串还是文件

照片、共享 Logo、大图片，以及任何需要缓存、搜索索引或频繁更新的内容，用图片文件。

小图标、单文件文档、邮件和 JSON 数据，用 Base64 字符串，因为基于文本的传输让文件不可能或不切实际。

两种形式承载的像素相同，所以选择取决于图片周围的系统，而不是图片本身。按传输方式、缓存和团队情况来选。

常见问题

Base64 图片比普通图片文件加载慢吗？

这取决于大小和场景。嵌入的小图标加载更快，因为它省了一次请求；嵌入的大照片加载更慢，因为它阻塞渲染、无法缓存。对大多数 10 KB 以上的图片来说，链接文件加载更快，尤其是在缓存有帮助的重复访问里。

能把 Base64 字符串转回文件，再正常托管吗？

可以。把字符串粘贴进 Base64 转图片工具，下载为原始、PNG、JPG 或 WebP 格式，上传文件到你的服务器。用文件 URL 替换嵌入的字符串，图片就重新变成一张正常的缓存文件。

Base64 图片在所有浏览器里都能用吗？

Data URL 在所有现代浏览器里都能用，包括 Chrome、Safari、Firefox、Edge。很旧的浏览器对 Data URL 有大小限制，但当前版本已经没有这些限制。邮件客户端是例外，有些仍然会屏蔽内联 Base64 图片。

嵌入几张图片之后，我的网页为什么这么慢？

因为嵌入的字符串让 HTML 文档大了很多，浏览器必须先下载全部内容才能渲染。每张图片还要多花 33% 的字节。把最大的图片移回链接文件，只保留小图标嵌入。

把用户头像以 Base64 形式存在数据库里安全吗？

方便，但本身并不安全。Base64 是编码，不是加密，任何能访问数据库的人都能把字符串解码成图片。大规模使用时，把头像以文件形式存在对象存储里，数据库里放一个引用；无论哪种方式，都要把数据库内容当作敏感信息对待。

API 里什么时候用分段上传代替 Base64？

大图片用分段上传，因为它直接发送二进制数据，没有 33% 的膨胀。API 只接受 JSON、小图片，或者客户端不容易构建分段请求时，用 Base64。很多 API 两种都支持，先看文档。
